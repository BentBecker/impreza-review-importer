# GitHub Updates — How It Works

This plugin supports automatic updates directly from a GitHub repository,
without needing to be listed on WordPress.org.

---

## How the Update Flow Works

1. **WordPress checks for updates** on a schedule (or when you visit
   Dashboard → Updates).
2. The updater class hooks into `pre_set_site_transient_update_plugins`.
3. It calls the **GitHub Releases API**:
   `https://api.github.com/repos/{owner}/{repo}/releases/latest`
4. The API returns the latest release tag (e.g. `v1.0.8`) and a `.zip`
   download URL.
5. The updater compares the remote tag to `RI_VERSION` defined in the plugin.
6. If the remote version is **higher**, WordPress shows the "update available"
   notice in the dashboard — just like any other plugin.
7. When you click **Update**, WordPress downloads the `.zip` from GitHub,
   unpacks it into `wp-content/plugins/reviews-importer/`, and the update
   is complete.

### Private Repositories
If the repo is private, add a **GitHub Personal Access Token** (classic,
`repo` scope) to `wp-config.php`:

```php
define( 'RI_GITHUB_TOKEN', 'ghp_xxxxxxxxxxxxxxxxxxxx' );
```

The updater will include it as a Bearer token in every API and download
request. Never commit the token to the repository.

---

## What You Need to Do Once

1. Create the GitHub repository (public or private).
2. Open `reviews-importer.php` and set the constant at the top:
   ```php
   define( 'RI_GITHUB_REPO', 'your-username/reviews-importer' );
   ```
3. To release an update:
   - Bump `RI_VERSION` in `reviews-importer.php` (e.g. `1.0.8`).
   - Commit and push to `main`.
   - Create a **GitHub Release** with tag `v1.0.8` and attach the plugin
     `.zip` as a release asset (or let GitHub auto-generate the source zip).
   - WordPress sites will pick up the update on their next check.

## Branching Structure

```
main
│   Production-ready code only. Every commit here is a releasable state.
│   Protected branch — no direct pushes; merge via pull request.
│
├── develop
│   Integration branch. All feature branches merge here first.
│   CI runs tests on every push. Merge to main when ready to release.
│
├── feature/short-description
│   One branch per feature or improvement.
│   Branched from develop, merged back into develop via PR.
│   Examples:
│     feature/google-reviews-source
│     feature/shortcode-columns-option
│     feature/admin-preview-refresh
│
├── fix/short-description
│   Bug fixes that go through the normal develop → main flow.
│   Examples:
│     fix/bom-stripping
│     fix/rating-bar-overflow
│
├── hotfix/short-description
│   Critical production fixes. Branched from main, merged into BOTH
│   main and develop so develop stays in sync.
│   Examples:
│     hotfix/activation-fatal-error
│
└── release/1.x.x   (optional)
    Used to freeze a version while last-minute polish is applied.
    Merge into main (tag it) and back into develop when done.
```

### Branch Naming Rules
| Prefix | Purpose | Base branch | Merges into |
|--------|---------|-------------|-------------|
| `feature/` | New functionality | `develop` | `develop` |
| `fix/` | Non-urgent bug fix | `develop` | `develop` |
| `hotfix/` | Urgent production fix | `main` | `main` + `develop` |
| `release/` | Release stabilisation | `develop` | `main` + `develop` |

### Commit Message Convention
```
type: short summary in present tense

feat: add Google reviews import source
fix: strip UTF-8 BOM on activation
chore: bump version to 1.0.8
docs: update readme with shortcode examples
```

### Release Checklist
- [ ] All feature branches merged into `develop`
- [ ] Version bumped in `reviews-importer.php` (`RI_VERSION`)
- [ ] Version bumped in `readme.txt` (`Stable tag`)
- [ ] `CHANGELOG.md` entry written
- [ ] `develop` merged into `main` via pull request
- [ ] GitHub Release created with tag `v{version}`
- [ ] `.zip` asset attached (or auto-generated by GitHub)
